# 《产品中心性能优化 Phase 1 完成报告》

## 结论

产品中心 Phase 1 保持既有正式链路：数据库筛选与排序后分页，只解析当前页关系和指标；列表状态保存在页面模块内，切换到其他模块再返回时不再重新请求已加载的产品列表。生产数据隔离副本中，50 条产品列表约 79KB，热请求为毫秒级；独立进程冷启动本轮抽样约 1.05–1.09 秒，属于服务启动后的单次初始化，不影响返回产品中心的热路径，因此不增加复杂缓存系统。

本报告按追加要求完成“全系统重复加载专项排查”。本次只修复与产品中心完全同类、可客观验证的启动数据重复请求，不改业务逻辑、数据口径、权限、状态机或数据库模型。

## 产品中心 Phase 1 结果

- 列表接口：`/api/product-center-v2/skus`，数据库分页，默认当前页面只渲染 30 条，接口上限 50 条。
- 查询顺序：筛选/排序 → 分页 → 当前页 Resolver → 当前页指标水合。
- 返回模块：`productSkuV2State.loaded` 保留已加载数据；筛选、排序、页码、子视图均继续使用现有页面状态，不建立第二套状态系统。
- 数据规模：50 条约 79KB，未出现为了当前页加载 6,906 个 ERP SKU 或全量关系解析的回退。
- 冷启动：隔离新进程约 1.05–1.09 秒；同进程热请求为毫秒级。该冷启动只在服务/模块首次初始化发生，按任务约束判定可接受。

## 全系统重复加载专项排查

### 排查方法

逐一核对一级模块的路由、首次请求、页面内 `loaded/loading` 状态、筛选/排序/页码变量和主应用渲染入口，并使用生产 SQLite 隔离副本已有性能基线核对数据规模。生产环境未发布本次代码，因此生产已登录页面仅用于确认旧版本行为；改动后的重复请求通过路由映射与缓存专项验证器验证，未对生产页面或数据执行写操作。

分级依据是用户等待与重复传输影响。当前没有发现本专项范围内因“返回模块重复加载”单独造成不可正常使用的 P0；但所有模块都会被整页重绘，数据较大的模块在低性能浏览器上仍可能产生可感知等待。

### 明显全量加载接口

1. 修改前，`task-waves`、`assessment-*`、`process-templates`、旧设置短路由、`template-center` 等路由没有统一映射到轻量模块，可能落入 `/api/data`，一次返回约 29.4MB 全系统快照。本次已统一映射，以上路由不再回退全量快照。
2. 任务使用服务端分页，关键行动使用 50 条服务端分页，产品使用 30–50 条数据库分页，目标详情使用 50 条分页；没有发现“数据库几千条 → API 全量返回 → 前端分页”的回退。
3. 工作结果接口仍返回有界摘要（任务不超过 1,000、计划不超过 100），不是业务全集，但当前约 0.94MB，已接近首屏上限，列为 P2 观察项。
4. 行动标准启动仍一次返回当前正式标准定义、节点与方法论，约 0.95MB；模板分类接口一次返回当前分类完整内容。当前规模可用，若继续增长应再做分类分页/详情按需，本次不因数据量尚小提前复杂改造。

### 本次顺手修复

1. 将原来只记住“当前模块”的单值判断改为按“当前用户 + 轻量模块”记录已成功加载的启动数据；返回已访问模块时跳过相同 bootstrap 和通知摘要请求。
2. 登录启动、刷新后的首次加载和模块切换统一使用同一缓存语义；显式业务写入后的 `loadPersistentData()` 仍强制刷新，不会被导航缓存拦截。
3. 统一正式路由与旧入口别名到轻量数据模块，堵住误回退 `/api/data` 的路径。
4. 管理驾驶舱的外层启动完成后同步标记已加载，消除页面绑定阶段再次请求同一 `dashboardManagement` 摘要的问题。
5. 退出登录时清空用户级启动缓存和管理驾驶舱状态，避免账号切换复用前一账号数据。

### 导航状态保持

本次直接复用页面已有状态，不新增全局状态框架：

- 任务保留 `taskListView`、`taskSort`、筛选条件、`taskListPage`、显示视图与当前页结果。
- 产品保留 `productSkuV2State` 中的筛选、排序、页码、子模块和已加载结果。
- 关键行动保留 `schedulePageState.page`、当前视图和已加载页。
- 工作结果保留统计周期和 `workResultsLoadedDays`。
- 模板中心保留当前分类、筛选、已加载分类和版本状态。
- 目标保留当前目标、Tab 与已加载详情集合；设置由现有 hash 保留当前设置子页。

因此“我的任务 + 截止时间排序 + 第3页”等状态在模块往返后仍由原页面变量恢复，不会重新回到默认状态。

### 未修复问题及原因

| 问题 | 证据 | 影响 | 优先级 | 本次不修原因 |
|---|---|---|---|---|
| 主应用每次模块切换执行 `app.innerHTML = …` | `src/main.js` 的统一 `render()` 重建侧栏、页头和当前页面 | 大页面会重复创建 DOM、重新绑定事件，可能出现闪烁和主线程占用 | P1 | 需要拆分应用壳和页面挂载生命周期，已超出“简单复用页面缓存”范围 |
| 行动标准一次装载完整定义关系 | 首屏约 0.95MB | 当前可用，数据继续增长后会增加解析和重绘时间 | P2 | 需要新增摘要/详情 API，当前体感影响较小 |
| 模板分类完整返回 | 行动分类按需约 0.77MB | 首次打开大分类存在等待 | P2 | 需要分类分页及详情契约，当前仍低于 1MB |
| 产品服务一次性冷启动 | 独立进程约 1.05–1.09 秒，热请求毫秒级 | 服务重启后的首次请求略慢，模块往返不受影响 | P2 | 为约 50–90ms 引入预热或复杂缓存收益不足 |

### 验证

- 重复加载专项验证器：22 个正式/兼容路由全部映射到预期轻量模块；登录、启动、模块切换均使用页面缓存；退出登录清理缓存。
- 页面现有状态保护：目标详情、关键行动页、任务列表、工作结果周期、模板分类和产品列表的既有缓存守卫均通过静态契约验证。
- `npm run check`：22 项现有测试全绿（16 + 6）。
- `git diff --check`：通过。
- 本次没有 Schema、Migration 或业务数据修改；所有数据库性能验证使用隔离副本。

## 最终优先级

- P0：无新增项。
- P1：主应用整页重绘；本次已解决的八个模块返回时重复 bootstrap/通知请求；管理驾驶舱首次双请求。
- P2：行动标准完整定义首屏、模板分类完整返回、产品单次冷启动。

结论：本次轻量专项已经确认“重复请求 + 整页重绘”是共性现象；重复请求和错误全量回退已用小范围机制修复，整页重绘作为独立架构改造候选保留，不应继续混入产品中心 Phase 1。
