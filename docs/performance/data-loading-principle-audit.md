# Performance-005 全系统数据加载原则审计报告

## 1. 审计结论

本次审计基于当前源码、只读生产数据库副本和服务端数据读取实现完成；未修改业务代码、数据库或生产数据。

当前系统并非整体都存在加载问题，而是呈现明显的两类架构：

- 产品中心、链接中心、数据中心的主要业务列表已经采用服务端分页或按视图加载，基本符合数据加载原则。
- 目标、关键行动、工作结果、财务、模板、设置等路由仍会先读取 `/api/data` 全局快照；任务中心和排期虽走 `/api/bootstrap`，但仍一次返回全部任务、流程实例和工作计划。这里是当前最主要的系统性风险。

只读副本实测的未压缩 JSON 体积如下：

|入口|返回体积|关键集合|
|-|-:|-|
|驾驶舱 bootstrap|2.14 MB|notifications 2,623 条及公共字典/模板|
|产品中心 bootstrap|2.14 MB|公共字典/模板，不含产品全集|
|链接中心 bootstrap|2.14 MB|公共字典及关系治理所需模板|
|任务中心 bootstrap|15.13 MB|tasks 5,934、processInstances 1,027、workPlans 958、notifications 2,623|
|排期 bootstrap|15.13 MB|与任务中心同一批全量任务/流程数据|
|全局 `/api/data`|25.16 MB|tasks 5,934、products 2,958、productErpMappings 2,956、erpGoods 2,091、processInstances 1,027 等|

结论：六项原则中，“详情按需加载”和“关系按需解析”在产品中心表现最好；“列表分页”“Tab 懒加载”“统计摘要”“前端渲染数量控制”在任务、目标、关键行动、工作结果、财务、模板和设置中仍有明显缺口。

## 2. 审计方法与口径

- “首次加载请求数量”指进入路由后由页面代码明确触发的数据请求，不包含图片、字体、静态 JS/CSS，也不把登录态请求计入。
- 对使用全局状态的旧页面，路由进入至少会先发生 1 次 `/api/data` 或 `/api/bootstrap` 请求；页面内部附加请求单独列出。
- 返回数据量来自只读生产数据库副本上按服务端当前序列化逻辑计算的原始 JSON 大小，不是浏览器压缩后的网络传输量。
- DOM 风险依据页面渲染代码是否对完整结果直接 `.map()` 判断；本次没有启动浏览器录制每个页面的实际 DOM 节点总数。
- “符合”分为：符合、部分符合、不符合。部分符合表示列表或详情中已有按需机制，但路由基础数据或某些 Tab 仍全量加载。

## 3. 六项原则总体符合情况

|原则|结论|主要证据|
|-|-|-|
|1. 列表分页原则|部分符合|产品、链接、数据中心已服务端分页；任务、目标、流程、财务费用、模板、设置主要在前端过滤/渲染全量数组。|
|2. 详情按需加载原则|部分符合|产品详情按 scope 加载；数据中心详情点击后加载；链接详情先加载较大的 core detail，部分 Tab 再按需加载。|
|3. Tab 懒加载原则|部分符合|产品详情和链接详情的附加 Tab 有懒加载；财务任意 Tab 首次进入同时请求 5 类数据；设置/模板依赖全局快照。|
|4. 统计摘要原则|部分符合|经营类页面多有专用摘要接口；任务、目标、工作结果和模板统计仍基于前端全量数组计算。|
|5. 关系按需解析原则|基本符合但有遗留|产品 SKU 列表已“分页后 Resolver”；链接详情按对象解析。旧全局状态页面仍装载大量关系数组，但未发现这些页面需要全量 Sales Object Resolver。|
|6. 前端渲染数量控制原则|部分不符合|任务、目标、流程、财务费用、模板资产、设置组织树等直接映射当前完整集合；财务导入仅前端 `slice(0, 200)`。|

## 5. 重点问题证据

### 5.1 全局快照回退是最大共性问题（P0）

`loadPersistentData` 只把 dashboard、products、connectionCenter、tasks、task-list、scheduleBoard 等少数路由列为轻量模块。其余路由直接请求 `/api/data`。因此目标、流程、工作结果、财务、数据中心、模板和设置即使自身只需要少量数据，也会获得约 25.16 MB 的全局 JSON。

这违反：列表分页、详情按需、Tab 懒加载、统计摘要和前端数量控制五项原则。它也是“页面专用接口已经分页但页面仍慢”的潜在原因：专用接口前面仍有一次大快照。

### 5.2 任务与排期的“轻量 bootstrap”仍不是分页（P0）

任务中心的 bootstrap 包含全部 `tasks`、`processInstances`、`workPlans`，当前只读副本分别为 5,934、1,027、958 条。任务表通过 `getFilteredTasks().map(...)` 在浏览器排序和渲染，未见服务端 page/limit。排期复用同一 bootstrap，未按日期窗口读取。

动态加载 JS 解决了首屏代码体积，但没有解决路由进入后的业务数据全量加载。

### 5.3 财务中心没有 Tab 数据隔离（P0）

`refresh` 每次同时请求 statement、analysis、entries、import batches、rules。用户只看财务首页时也会加载费用、导入批次和规则；切换 Tab 只是重渲染已有数据。导入预览用 `rows.slice(0, 200)` 控制 DOM，但服务端结果已经全部到达浏览器，属于前端截断而非分页。

### 5.4 产品中心已形成正确范式

SKU 列表采用“筛选/排序 → SQL 分页 → 当前页 Resolver → 当前页指标水合”，默认 50 条；Metadata 直接聚合，不执行全量 Resolver。详情采用 summary + scope，Tab 首次进入才加载并缓存。这是其它列表/详情应对齐的基线，但本报告不提出代码变更。

### 5.5 链接中心是部分按需，不是完全按需（P1）

列表和治理队列具备服务端分页，诊断/销售扩展/advanced Tab 也会在首次进入时加载。问题在于 core detail 一次带回销售、产品、库存和 SKU 销售等多个区块，用户只查看基础信息时仍会得到非当前区块数据。

### 5.6 全量关系解析风险已明显下降

产品 SKU 列表已不再对约 6,902 个 ERP SKU 做全量 Resolver，而只处理当前页。此次扫描未发现任务、目标、财务、模板或设置页面主动执行全量 Sales Object Resolver。当前“关系按需解析”的主要遗留不是 Resolver 本身，而是 `/api/data` 仍携带 `productErpMappings` 等关系数组。

## 6. 违规模式清单

|模式|发现位置|等级|影响|
|-|-|-|-|
|全量数据库快照后前端筛选|目标、关键行动/流程、工作结果、财务、数据中心、模板、设置|P0|固定约 25.16 MB 基础响应；序列化、网络、解析、内存共同增加|
|业务全集 bootstrap|任务、排期|P0|约 15.13 MB；任务增长直接增加浏览器计算与 DOM 风险|
|前端分页/截断|财务导入预览 `slice(0, 200)`；部分排行 `slice(0, 20)`|P0/P1|控制了显示数量但没有控制查询和传输数量|
|打开页面加载全部 Tab 数据|财务中心|P0|5 个页面数据接口同时调用，隐藏 Tab 也付出成本|
|全量前端统计摘要|任务、目标、工作结果、模板使用次数|P1|当前数据尚可运行，但随任务/流程历史线性或多重扫描增长|
|详情核心接口跨区块过取|链接详情|P1|只看基础详情也加载销售/产品/库存/SKU 销售数据|
|历史/异常列表无服务端分页|数据同步中心|P1|同步批次和异常累积后响应与 DOM 持续增长|
|大关系数组随全局快照下发|所有 `/api/data` 回退路由|P1|即使没有执行 Resolver，也产生不必要传输与解析|
|完整组织树/配置列表一次渲染|设置|P2（数据小）|当前数据规模风险有限，组织规模增长后放大|

## 7. 优化优先级（仅审计结论，不实施）

### P0：立即进入后续优化评估

1. 取消目标、关键行动/流程、工作结果、财务、数据中心、模板、设置对 `/api/data` 的默认依赖，建立各路由最小 bootstrap 契约。
2. 任务中心改为服务端筛选、排序和分页；任务详情再读取关联流程、记录和附件。
3. 排期按可见日期窗口和人员范围查询，不读取全部任务。
4. 财务中心按当前 Tab 请求数据；费用、批次、规则服务端分页；导入预览由服务端分段返回。

### P1：数据增长前完成

1. 关键行动、目标和工作结果建立摘要接口与明细分页，避免浏览器扫描全量任务/流程。
2. 链接详情将 core detail 拆成真正的基础详情和 Tab scope 数据。
3. 数据同步中心为批次、异常和日志增加分页边界。
4. 模板中心将模板资产列表及“使用次数”改为后端摘要，版本详情继续按需加载。
5. 把公共 bootstrap 中 notifications、模板和字典按用户首屏实际需求继续收窄。

### P2：轻微优化

1. 设置页按 Tab 获取大型配置集合；小型组织/权限字典可继续同步加载。
2. 对产品、链接现有分页接口持续增加响应大小与 Resolver 调用数回归测试，防止未来回退。
3. 图片继续使用 `loading="lazy"`，并为长卡片列表保持虚拟化或明确分页上限。

## 8. 建议验收基线

后续每个页面优化时，应至少记录并守住以下指标：

- 路由首次业务请求数；
- 首次 JSON 未压缩/压缩体积；
- 列表默认 pageSize 和最大 pageSize；
- SQL 返回行数与最终页面行数；
- 当前页 Resolver 输入数量；
- 隐藏 Tab 是否产生请求；
- 详情首开返回字段范围；
- 首屏 DOM 节点数量；
- P50/P95 接口响应时间。

建议原则性门槛：普通列表默认返回不超过 50 条；任何页面不得通过“后端全量返回 + 前端 slice”冒充分页；隐藏 Tab 默认零业务请求；列表 Resolver 输入不得超过当前页对象数量。

## 9. 最终判断

当前系统的数据加载原则执行程度为“部分达标”。产品中心已经提供可复用的正确范式，链接中心和数据中心的业务接口也具备较好的分页基础；真正的系统级阻断是旧页面仍依赖全局数据快照，以及任务/排期仍以业务全集作为页面状态。

建议后续优化顺序为：全局快照路由拆分 → 任务/排期服务端分页与窗口查询 → 财务 Tab 懒加载 → 关键行动/工作结果摘要化 → 链接详情 scope 收窄。此顺序可以先消除最大网络与解析成本，同时不触碰业务规则。
